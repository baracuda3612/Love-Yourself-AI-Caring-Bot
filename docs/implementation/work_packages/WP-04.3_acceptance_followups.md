# WP-04.3 — конкретні незакриті acceptance-перевірки

За рішеннями засновника 2026-11-05 та 2026-11-07. Ці сценарії входять до
приймання відповідних WP після закриття B4 для інтеграції.

Джерело: незалежна повна перевірка dd65797ecdc061702832efc32bdad14924a0cc33
та [PR #273](https://github.com/baracuda3612/Love-Yourself-AI-Caring-Bot/pull/273),
змерджений у `88d39a4`. Для наведених нижче перевірок докази ще потрібні.
Поточний статус усіх рядків: **NOT_PROVEN**. Наявні mock/adapter/code-trace
результати залишаються доказами у своїх межах, але не закривають ці рядки.

## Сценарії та очікувані результати

**A43-01 — Telegram на пристроях.** На iOS та Android пройти вхід, введення
неправильного/правильного часу, перевірку, всі три редактори, helper article
і повернення з незастосованою чернеткою днів, confirm, Мій розклад/Мої дані/
Про проєкт/Підтримка; pause/resume та cancel завершення. Перевірити перемикач
нижньої клавіатури, її зміну до/після setup, одночасну доступність inline дій,
hide/show клавіатури, закриття/повторне відкриття чату, повторне й старе
натискання, деградацію OpenAI. Очікується: доступні потрібні кнопки без команд,
прогрес/чернетка збережені, повернення на правильний крок, один перший план,
жодного setup тексту в Coach/history, правдива наступна дата й відсутність
дублікатів ефектів. Потрібні запис проходження/скріншоти обох платформ,
версії OS/Telegram та звірка DB/receipts для того самого тестового акаунта.

**A43-02 — справжній cross-app handoff.** Від company/test link відкрити
браузер → реальний тестовий mailbox або кожен configured OIDC → Telegram.
Перевірити cancel/return із provider, неправильний/прострочений email code,
повтор коду/одноразового handoff, прострочений link і retry; відкритий та
закритий Telegram, повернення в браузер, відкриття політики зі збереженням
введеної адреси. Очікується: лише configured methods, нейтральні відмови,
правильний actor/environment/enrollment, одноразове погашення без другого
акаунта/плану та працездатний шлях повтору. Не достатньо mocked provider,
перехопленого POST або намальованого deep link. Доказ: device/browser trace
із редагованими ідентифікаторами плюс мінімальні DB receipts; коди/tokens
не публікувати. WP-10.2 додатково перевіряє corporate browser/network.

**A43-03 — реальний persistent scheduler.** Використати release-configured
persistent jobstore та нові ізольовані PostgreSQL дані. Після зміни днів/поясу
спричинити реальну недоступність jobstore на межі DB commit → effects.
Повернути сховище, повторно застосувати той самий вибір; окремо перезапустити
процес між commit і effects. Очікується: committed preferences/dates збережені,
немає хибного повідомлення про успіх, всі jobs відповідають current DB state,
retry не рухає timestamps/expiry/version повторно, due work не губиться і
не дублюється, immutable attempts та paused/report-blocked стан не обходяться.
Доказ: автоматизований тест із керованими barriers, snapshots DB/jobs/receipts
до/після та логи restart/recovery. Підміна schedule_plan_step exception і
in-memory scheduler самі по собі цей рядок не закривають.

**A43-04 — cutover/restore.** На ізольованому релізному середовищі виконати
stop-old → перевірка відсутності старого polling/scheduler writer → rehearsed
migration/start-new → readiness/smoke. Окремо виконати дозволений сценарієм
rollback або restore backup з reconstruction jobs. Очікується: нуль перекриття
старого/нового writer, точні schema/content/config/artifact versions, один
набір jobs, збережені delivery/unknown-send факти без повторного надсилання,
працездатний recovery. Доказ: часовий журнал PID/replica/writer, manifest,
backup/restore та DB/job/receipt перевірки. Опис runbook без виконання не PASS.
Це доручення майбутнім WP, не дозвіл зараз змінювати durable environments.

**A43-05 — DST і конкурентність.** У контрольованому часі пройти весняний та
осінній переходи Europe/Kyiv, а також fixed UTC override як контроль.
Конкурентно виконувати calendar edit і scheduler claim/send на межі due часу;
включити повтор/рестарт, уже due/delivered/attempted крок, pause та
report-blocked successor. Очікується: дозволені майбутні кроки слідують
прийнятому локальному розкладу, fixed UTC не отримує сезонного зсуву;
due/delivered/attempt факти незмінні, одна logical occurrence не надсилається
двічі, receipt відповідає реально обраній даті, successor не обходить report.
Gap/fold локальних часів мають відповідати чинному delivery contract;
не вигадувати нову DST-політику в тесті — невизначеність контракту винести
на рішення до закриття. Потрібен actual lifecycle + delivery claim/receipts
на PostgreSQL, deterministic barriers/time і перевірки jobs, не лише ZoneInfo
unit test або sleep-based stress.

**A43-06 — політика.** Після затвердження перевірити, що
/enroll/privacy-policy показує остаточний документ замість draft, посилання
форми й розділ приватності бота ведуть до погодженого повного документа,
а actual deployment notice pin/receipt відповідають затвердженій версії.
Repin вимагає нового ознайомлення; відсутній/retired notice не відкриває Coach.
Доказ: затверджена версія/digest, перевірка сторінки/бота й exact receipt.
Самої заміни заголовка або статусу файла недостатньо.

## Як не загубити залишки

У handoff/acceptance evidence кожного вказаного WP мають бути його A43-ID,
конкретний test/run reference, exact Git SHA/image/schema/config, середовище,
expected/actual та evidence location. Для WP-09.1 потрібні executable tests
і successful canonical run, для WP-09.4 — release-candidate виконання, для
WP-10.1/10.2/10.3 — відповідні документальні та deployment докази. Це конкретні
exit criteria цих WP, не необов'язковий список «перевірити пізніше».

NOT_PROVEN не стає PASS від самого merge або нового code review. При FAIL
фіксується відтворюваний дефект із власником відповідного компонента; не
замінювати його checklist tick. Непроведені перевірки лишаються відкритими
у відповідному WP та на чинному beta/production gate. Історичні audit verdicts
не переписуються; нове виконання додає окремий доказ для свого кандидата.
