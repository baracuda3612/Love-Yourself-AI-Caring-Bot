# WP-01.4 — Establish event, privacy, and deployment primitives

## Objective

Give later packages one truthful event operation and the durable schema
authorities required for deployment attribution, access chronology, privacy
notice evidence, feedback, revocable reports, and independent aggregates,
without claiming that those later behaviors are implemented.

## Preconditions and bookkeeping

WP-01.3 is `VERIFIED`. Founder merged PR #254 as
`285d84f571cf8f206e4eed2e511916d86e641ec0`; the first change on this branch
records that closeout in the roadmap and WP-01.3 package document.

The package uses repository evidence and disposable local PostgreSQL only. It
does not connect to Railway, inspect secrets, apply the migration to the target
deployment, or mutate real data. The target build must not start against the
old Railway schema.

## Delivered authority

* Revision `20260905_event_privacy` adds deployment, restricted access identity,
  roster, entitlement, invitation, enrollment, notice acknowledgement,
  feedback, report-grant, event-catalogue, and aggregate structures.
* `users.first_seen_at` is set for new users by the server and is immutable.
  Legacy users are backfilled only from the earliest stored event/chat/plan
  timestamp with a provenance marker; users without chronology stay null.
* Canonical events have an allow-listed name/schema/kind and property schema,
  stable source operation, occurrence/recording timestamps, environment,
  timezone bucket/basis, and explicit deployment/plan/step/content snapshots.
* Plan-step linkage is an integer FK. Exercise and positive content version use
  a composite `MATCH FULL` FK. The writer derives all four plan/content fields
  from the authoritative plan step and catalogue row and never manufactures
  catalogue content.
* `write_event_operation()` inserts one personal event and one independent,
  bounded personal contribution inside the caller's transaction. Database
  uniqueness plus conflict verification makes sequential and concurrent retries
  return the same rows; source-operation reuse for another fact is rejected.
* Operational events are catalogue-distinct from user behavior. Properties
  reject non-catalogued keys, raw identity, free text, and diagnostic payloads.
* Contribution rows have no event join key. Sealed cells forbid personal/source
  identifiers and are immutable; correction/sealing behavior remains WP-07.3.
* The complete legacy event boundary and removal owners are recorded in
  `docs/implementation/wp_01_4_event_compatibility_manifest.md`.

## Migration and compatibility boundary

Existing event rows are not assigned guessed canonical fields. Their legacy
columns remain unchanged and canonical columns remain null. New writers leave
the legacy columns null and no longer create plan instances, execution windows,
content stubs, mutable task counters, or inferred failure signals.

The cutover is stop-the-world: stop old runtime processes, apply the forward
revision, then start only the exact-head build. There is no old-binary rollback.
For disposable local data rollback means drop/recreate; any future durable
database requires Gate G1 restore evidence and a reviewed restore/forward-fix
decision.

## Scope boundaries preserved

This package does not:

* instrument or reconcile every feature path (WP-07.1);
* implement privacy export, retention jobs, or deletion (WP-04.2);
* implement entitlement, invitation redemption, or enrollment behavior
  (WP-04.1);
* implement delivery/callback reconciliation (WP-03.4);
* create on-demand occurrence storage or behavior (WP-06.1/B6);
* seal/report company metrics, dashboards, or founder reports (WP-07.2/07.3/B7);
* add a generic outbox, universal lock framework, warehouse, partitioning, or
  speculative production infrastructure;
* run a Railway migration/deploy, inspect secrets, or mutate real data.
