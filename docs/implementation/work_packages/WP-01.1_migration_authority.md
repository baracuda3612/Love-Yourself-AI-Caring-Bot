## Objective and bounded exception

Establish a reproducible PostgreSQL migration ledger before target-schema
refactoring. During this package the existing founder testnet remains explicitly
disposable and is inspected read-only. Paid backups, a scratch restore, and
measured RPO/RTO remain Gate G1 prerequisites before durable data, company-user
enrollment, production migration, or market launch.

## Read-only physical evidence

The 2026-08-27 content-free inspection used a database-level read-only
transaction against PostgreSQL 17.11. It read schema metadata and aggregate
counts only; no Telegram identifiers, names, messages, profile content, facts,
notes, event context, or serialized scheduler payloads were selected.

| Evidence | Observed |
|---|---:|
| Physical tables | 18 |
| Application-owned tables | 17 |
| APScheduler-owned tables | 1 (`apscheduler_jobs`) |
| Columns | 166 total; 163 application-owned |
| Enum labels | 47 across 12 enum types |
| Constraints | 48 |
| Indexes | 42 |
| Alembic revisions | none |
| Users | 2 |
| Plans / drafts / plan instances | 1 / 1 / 1 |
| Scheduler jobs | 6 future; 0 past due; 0 paused |

The aggregate lifecycle inventory found one `IDLE_NEW` and one `IDLE_FINISHED`
user, one completed plan, one finalized draft, and step rows split across
`completed`, `expired`, and `skipped`. This confirms the database is small
founder-only test data while still exposing the real legacy schema surface.

Material physical drift that the baseline must preserve rather than silently
repair includes:

* no `alembic_version` ledger;
* legacy lifecycle states in `ck_users_current_state`;
* legacy `ai_plan_steps.time_of_day` and `job_id` columns;
* physical `user_daily_logs` names that differ from current ORM attributes;
* duplicate draft/draft-step indexes;
* unused duplicate enum families left by historical ORM and SQL paths;
* ORM/physical differences in enum use, nullability, defaults, and types.

Those are starting-schema facts, not accepted target design. WP-01.2 and later
owners decide their forward cleanup.

## Implemented authority

* Alembic 1.19.1 is a direct locked dependency.
* `20260827_schema_baseline` is the single Alembic root/head and reproduces the
  inspected application-owned schema on an empty PostgreSQL database.
* The old disconnected one-off Alembic file is removed from the active ledger;
  historical raw SQL remains non-authoritative evidence only.
* `make migrate` is the single forward command (`alembic upgrade head`).
* The local migration harness creates and removes one uniquely named disposable
  PostgreSQL database and can compare it with a sanitized inspector snapshot.
* Runtime startup no longer calls `Base.metadata.create_all()`. It performs a
  read-only `alembic_version` check and fails closed on incompatibility.
* `apscheduler_jobs` is excluded from Alembic ownership and covered by the
  separate restore/reconciliation procedure in
  `docs/deployment/database_migrations.md`.

## Existing testnet adoption

The initial inspection did not stamp or migrate the Railway source database.
After review confirmed the exact physical comparison, the founder authorized
the one-time adoption stamp. Railway now contains the single ledger revision
`20260827_schema_baseline`, verified by a subsequent read-only inspection. The
stamp added only `alembic_version` and its one revision row; it did not execute
the baseline DDL against, or change data in, the 17 existing application tables.

## Rollback

Revert the package commit to restore the previous runtime and dependency state.
The baseline downgrade is intentionally unsupported: a baseline is an adoption
boundary, not a data rollback tool. Normal rollback deploys only code compatible
with the current forward schema. A future destructive recovery uses the Gate G1
restore procedure and its measured RPO/RTO.
