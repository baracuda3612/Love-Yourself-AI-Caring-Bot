# WP-03.4 — Reconcilable scheduled delivery and callbacks

## Bounded execution contract

Integration base: `359493acc577ccd3f2ce73a51e97a290e941f7ea` (merged PR #264).

Scheduled sends use one stable operation per plan step, with separate numbered
attempts. PostgreSQL records the claim before Telegram and the actual immutable
presentation, payload, variant and chat/message receipt after confirmation.
The failure-recovery path follows the Safety Car contract: concrete failures
arm one-shot recovery at the next useful time; successful ordinary traffic does
not enable a recovery interval. Startup restores unfinished work once. Repaired
history cannot consume per-user sessions/locks or alter performance/event facts.
Only definite retryable rejections may retry, at most three attempts within the
existing two-hour delivery grace and action deadline. Unknown outcomes, including
interrupted in-flight attempts, remain quarantined: Telegram has no send
idempotency key or message lookup that can safely prove non-delivery. A late
receipt or an owned callback on the sent message can reconcile the result;
uncertainty never causes another send. No opportunity event precedes confirmation.

The existing lifecycle lock order owns Done/Skip/expiry and their event writes.
Only a delivered step accepts Done/Skip, before its existing deadline; pause
preserves that action, cancel closes it. Duplicate and late taps describe the
winning state. Terminal UI edits the receipt's original text or GIF caption,
keeps instructions, and retries failed edits after restart. Optional efficacy
feedback is completed-only, one immutable better/same/worse answer per owned
step, with its event committed together. Feedback does not affect selection.

Preserve exact-version DB content authority, DG-02 medical gating, one-message
presentation, and independence from OpenAI. DG-03 device previews, thumbnail,
caption placement and weak-network behavior remain beta checks. No on-demand
occurrences, automatic plan completion, engagement, retention, new media,
universal queue or unrelated legacy cleanup. The 21 known completion/report/
metrics failures remain outside this package.

## Implementation and verification — 2026-10-10

`20261010_scheduled_delivery` adds numbered scheduled attempts, immutable receipt
guards, one open/successful attempt per step, feedback uniqueness and allowed
efficacy values. The scheduler journals the claim before send, persists late
results inside the coroutine, retries receipt writes without another send, and
restores due work once at startup. Concrete send/UI failures arm one-shot
recovery; repaired work stops it. Interrupted sends are quarantined.

The lifecycle boundary owns confirmed delivery, Done/Skip and their events,
late-tap expiry, and completed-only feedback. Pause preserves delivered actions;
cancel wins without reopening a step when a late receipt arrives. Terminal
text/caption projection retains immutable delivered instructions and Telegram
identity. Its worker-owned HTTP session permits bounded edits under the user
lock without blocking the polling loop's existing synchronous controls. Failed
edits retry after restart. The inherited completion job seam is preserved for
WP-03.5; callbacks no longer send engagement messages.

## GitHub finding and Safety Car remediation

GitHub reviewed `6ca5729a6067a552046b4f79300c7f367b5859ac` and reported one
P1: the recovery interval selected every confirmed historical receipt and
reacquired user locks despite an already aligned terminal UI. This was absent
from the frozen local inventory above. Accepted: select only stale terminal
status/efficacy projections with NULL-safe comparison before user locking.

The founder additionally requires event-driven failure recovery and an
independent audit of wasted CPU, memory, queries, locks and time across the
entire WP, including second-order effects and distortion of normal flow or
performance metrics. The permanent recovery interval is removed; only concrete
failures arm a one-shot job. Definite consumed retries close their previous
attempt, paused retries park until resume/window closure, and unknown sends
remain quarantined without another send. Normal expiry is a product deadline,
separate from the fault-recovery path.

The corrected candidate requires a new independent full-WP review before push.
No automatic GitHub review is retriggered by this remediation.
