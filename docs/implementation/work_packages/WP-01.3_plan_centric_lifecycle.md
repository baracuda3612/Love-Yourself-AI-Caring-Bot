## Objective

Make the plan aggregate the only durable lifecycle authority. Derive one
`current_mode` from onboarding progress and the one current plan, route plan
and step mutations through an operation-locked service, and migrate legacy
rows without inventing chronology or retaining synchronized mirrors.

## Delivered authority

* `ai_plans.status` uses normalized `active | paused | completed | abandoned`;
  `ai_plan_steps.step_status` uses
  `pending | delivered | completed | skipped | expired | canceled`.
* `app.lifecycle.derive_current_mode()` is the shared derivation for
  `ONBOARDING`, `ACTIVE`, `ACTIVE_PAUSED`, and `NO_ACTIVE_PLAN`.
* A partial unique index permits at most one `active` or `paused` plan per
  user; `(user_id, cycle_number)`, plan/day, and day/step order are unique.
* Deferred PostgreSQL constraint triggers enforce exact day count, non-empty
  days, and no open child step under a terminal plan at transaction commit.
* User-row locking serializes lifecycle work. Immutable
  `plan_lifecycle_operations` receipts make stable source-operation retries
  idempotent; conditional step transitions give concurrent terminal actions
  one winner.
* Activation, pause, resume, abandon, completion, delivery, user complete/skip,
  scheduler expiry, and cancellation now use the lifecycle service. Plan
  creation/finalization runs under the same user lock, assigns monotonic cycle
  identity, and returns a truthful duplicate result without replaying activation
  side effects.
* Coach/UI/scheduler readers use plan status and calculated progress. The
  retired generic snapshot writer and admin `/spawn` structural writer reject
  mutation.
* `apscheduler_jobs` remains owned exclusively by APScheduler and outside
  Alembic.

## Migration and compatibility boundary

Revision `20260902_plan_lifecycle` expands the schema, rejects ambiguous rows,
backfills only evidence-backed facts, converts normalized enums, creates
constraints/indexes/receipts, and then clears legacy mirrors. In particular:

* timezone-aware start/creation facts prove activation; the ambiguous legacy
  timezone-less `activated_at` value is not trusted, and an abandonment without
  a recorded end time aborts;
* plan duration/day topology must prove exactly 7 or 14 ordered non-empty days;
* boolean completion without a timestamp proves `completed` but is preserved
  with `terminal_at = NULL` and grandfathered `version = 0` rather than an
  invented time;
* multiple current plans, contradictory terminal evidence, unsupported
  statuses, invalid chronology, duplicate ordering, and unprovable onboarding
  abort the transactional revision;
* `users.current_state`, `user_profiles.is_paused`, scheduled end dates,
  `current_mode`, `current_day`, and legacy day/step completion mirrors are
  cleared and stripped of defaults after their evidence is copied.

The cutover is intentionally stop-the-world for lifecycle writers: stop every
old poller/worker/scheduler, migrate, then start only the build pinned to the
new Alembic head. There is no mixed-version writer interval and no old-binary
rollback. Recovery is a reviewed restore or forward fix. The complete consumer
and removal-owner map is
`docs/implementation/wp_01_3_lifecycle_compatibility_manifest.md`.

## Migration rehearsal evidence

`scripts.test_migrations` now creates two uniquely named disposable databases:

1. baseline → seeded legacy rows → head → repeated head, with schema inventory,
   evidence backfill, cleared mirrors, and APScheduler exclusion checks;
2. baseline → ambiguous duplicate current plans → expected transactional abort
   → baseline/DDL rollback proof → evidence-based remediation → head → repeated
   head.

On the migrated database it also runs real concurrent SQLAlchemy sessions:

* two identical activation retries produce one plan, one receipt, and one
  truthful duplicate result;
* two identical pause retries produce one mutation and one receipt result;
* reusing a source operation ID for another transition is rejected;
* reusing a step operation ID for another child target is rejected;
* a second current plan is rejected by the partial unique index;
* concurrent complete/skip attempts on one step produce one terminal winner;
* retrying the winning operation is a duplicate;
* abandon cancels the remaining open children once and retries idempotently;
* completion of an all-terminal aggregate commits once and retries
  idempotently.
* invalid enum values, reversed plan chronology, missing terminal timestamps,
  out-of-range days, and open children under a terminal plan are rejected.

Every database is explicitly dropped after the rehearsal.

## Rollback

The Alembic downgrade intentionally refuses because it would need to recreate
discarded duplicate lifecycle truths. Before non-disposable migration, Gate G1
requires a verified backup/restore drill. During this founder-only phase,
rollback means dropping the disposable rehearsal database; after a real
cutover, use the verified restore artifact or a reviewed forward fix. Reverting
application commits alone must not be paired with the migrated schema because
the old build is revision-pinned and its writers are not compatible.
