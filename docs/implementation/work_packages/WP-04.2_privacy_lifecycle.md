# WP-04.2 — Minimum privacy and data-rights lifecycle

Status: implementation candidate, not a deployment/release approval.
Base: integration `1f491eea1a942f80b7894645c40190c2a3cb9335` (PR #270).

## Bounded execution contract

The package implements notice acknowledgement, retained conversation authority,
restricted data-rights operations, account erasure and report-link authority.
It does not redesign onboarding/menu, metrics/company reports, legal roles or
contracts, general monitoring, or release controls. WP-04.1 environment,
entitlement and ownership checks remain authoritative. B3 content versions,
medical eligibility, actual receipts, uncertain-send quarantine, owned actions,
completion chronology and useful-time recovery remain intact.

| Failure / second-order effect | Contract / bounded response | Avoided waste |
|---|---|---|
| Notice changes after prior acknowledgement | Deployment pin changes explicitly; old immutable acknowledgement proves only the old text; new freeform storage/Coach requires the new version | No inferred consent, global policy fallback or historical rewrite |
| Missing, partial, stale or unavailable Redis | Read retained PostgreSQL, rebuild bounded TTL snapshot; failure cannot recover stale text | No cache business authority or duplicate conversation writer |
| Cache write races erasure | Same PostgreSQL user lock serializes worker-thread cache writes against deletion fence; post-fence writes see inactive/missing user | No new coordination authority in Redis |
| Conversation reaches 90 days | Indexed expiry batches; reads/exports exclude text before physical cleanup; source-linked feedback copies expire too | No permanent full-table scan, partitions or archive layer |
| Redis/scheduler erase fails | Committed inactive user and durable deleting request remain; retry same operation; no success claim | No generic outbox/recovery framework |
| Old or copied report URL | Opaque 7-day hashed purpose/deployment/runtime/key-scoped grant plus current owner access; neutral failure | No stateless signed-plan fallback |
| Sensitive legacy table has data | Transactional migration stops before any schema changes; founder reviews actual rows at G1 | No silent loss or promotion of testnet history |

## Authorities and erasure order

`chat_history` is the only durable conversation source. `notice_acknowledgements`
references immutable exact text/digest and deployment pin; Telegram callbacks
supply version-specific acknowledgement time and source operation. No old
acknowledgements are synthesized. An unpublished/retired notice fails closed.

`privacy_requests` is a restricted operational queue, not behavioral telemetry.
Private Telegram identity verifies a bot request. Manual email intake records
actual receipt time and a case UUID before verification; the subject confirms
that case from the original private bot account. Arbitrary email, internal
user id or a case number alone never authorizes export or erasure.

The one erasure service commits a user fence and grant revocation, confirms
Redis and scheduler cleanup, then transactionally removes personal events,
contributions, feedback, grants, plan obligations/receipts and children, draft
children, legacy execution rows, conversations, notice receipts, enrollment,
profile and user. Unshared access identity, proofs, invitations, entitlements
and roster membership rows are erased too. A shared access identity remains only when another account owns it;
the deleted account retains no enrollment or join to that authority. Independent sealed aggregates are neither changed nor manufactured.
Final restricted case receipts contain an opaque UUID, times, support owner and
fixed result, with no subject/Telegram operation join key, and expire after
90 days. Already claimed network I/O can finish; the fence prevents fresh
access and delivery claims. Deletion is forward-only and repeatable.

## Retention and log boundary

Conversation deadline is at most creation +90 days. Unknown legacy creation
time expires at cutover, rather than receiving an invented fresh lifetime.
Retained reads use the `(user_id, created_at, id)` index; cleanup uses
`(expires_at,id)`, at most 500 roots per transaction and ten batches per
five-minute maintenance cycle. Deletion retries are selected least-recent-attempt
first, with a committed attempt timestamp before external cleanup, so a failed
head cannot starve later cases. Source-linked feedback is removed before its
chat FK target. Feedback and completed case receipts have indexed bounded
expiry cleanup. Expired text cannot enter support exports.

Redis keys are environment/version namespaced. Message snapshots contain at
most 20 retained messages, timestamps and expiry; TTL is the smaller of one
day and the earliest message deadline. Every read validates against durable
truth. Pending-action TTL is at most one hour and writes use the same user
fence. Missing Redis only loses convenience. New message writes invalidate;
account erasure confirms deletion of current and known legacy session keys.

Runtime LogRecords emit source location/exception class, plus the reviewed
numeric retention count. They do not emit conversation bodies, tool arguments,
URLs, provider exception bodies, SQL bind parameters or tracebacks. Remote
report fonts were removed and personal HTTP responses prohibit caching and
referrer disclosure. This code cannot retroactively purge hosted logs/backups:
historical content logs must be deleted or verified <=90 days, and hosting
backup expiry/restore erasure must be evidenced before beta/G1. No private
journals or historic user logs were read in this package.

## Model request boundary

All live Responses API entries explicitly set `store=False`; no provider-side
conversation, prior response id or account metadata is attached. Coach history
is limited to 20 turns of at most 4000 characters each; the current turn is
bounded too. Final provider-request tests contain sentinel identity metadata
and prove it is absent from the emitted request. User-authored text can itself
contain volunteered personal information, which the reader draft discloses.
No claim of zero provider retention is made. The obsolete alternative pulse
client adapter was removed; production uses Responses exclusively.

- Intake from bot: `/data_request access`, `export`, `correction` or `deletion`.
  `/request_status` shows the subject's last ten case records even after
  entitlement expiry. No false receipt is returned if persistence fails.
- Intake from email: `python -m scripts.privacy_admin --operator hello@loveyourselfua.com receive-email --kind export --received-at <actual-UTC-ISO-time>`.
  Reply manually with case UUID and `/data_request export <case-UUID>` for the
  original private bot account. Do not issue data to the original email address
  merely because it sent the request. If the account is unavailable, keep the
  case unverified; use reviewed ownership recovery under WP-04.1/04.3 before
  linking it. Do not collect passports by default.
- Check `... queue` every working day; it includes verification, owner, deadline
  and overdue status. If `next_after` is non-null, continue with
  `... queue --after <next_after>` until it is null. Pages contain at most 100
  requests, ordered by deadline and case UUID; completed anchors still permit
  continuation. A full first page is not proof there are no later requests. Internal response target: 30 days from actual receipt.
  No automatic silent extension. Escalate unresolved cases before the deadline.
- `... export <case-UUID> --output <private-new-path>` creates an owner-only JSON
  copy without bearer secrets, other roster members or expired conversations.
  Review it, agree delivery with the verified subject, and use the verified
  private account or another separately verified delivery channel. Remove the
  temporary file immediately after successful delivery, at most seven days
  after creation. Record `... complete <case-UUID> --evidence delivered_to_verified_subject`
  only after actual delivery. Generation alone is not fulfillment.
- `... correct <case-UUID> --changes-file <private-JSON>` accepts only name
  preference and communication style. Schedule/timezone/identity corrections
  use the existing owned services and verification; historical actual events
  and receipts are never rewritten. Deliver the result to the verified subject
  and record `correction_confirmed` or `manual_resolution_delivered`; a refusal
  needs a human explanation, not a silent completed flag.
- `... delete <case-UUID>` begins the one durable erasure operation. The live
  scheduler worker finishes external cleanup and database erasure. Before this
  step remove temporary exports and subject content from support working files
  and mailbox as applicable. `deleting` is not success. Confirm `completed`
  with `... status <case-UUID>` and send the human completion response through the
  previously verified support channel. Preserve only the minimal case receipt;
  remove subject content from the support mailbox and working files. A failed
  external store leaves the case pending for retry; never toggle user activity
  to bypass it.

This is a manual, identity-checked support workflow, not a new public data API.
The operator is responsible for mailbox delivery/erasure evidence; the code
proves database/Redis/scheduler completion. The current UI remains minimal;
WP-04.3 owns polished placement and device transitions.

## Migration, compatibility and rollback

Revision `20261022_privacy_lifecycle` follows `20261015_access_authority`.
Stop all old binaries before migration, require Gate G1 before any durable
cutover, and start only this schema-head build. Legacy stateless links stop
working; unscoped stored grants are revoked. There is no token or deployment
backfill. Notice text is nullable for old versions, which remain unusable
until an approved new exact-text version is explicitly installed/pinned.

No deployed database was inspected or migrated. Code search found no accepted
UserFact/UserDailyLog writers/readers; existing ORM/physical-column drift also
confirmed they were speculative. The migration locks and proves the actual
target tables empty, otherwise rolls back. It then removes both tables and
unused fact enums. Disposable tests cover nonempty refusal, transactional
rollback, explicit remediation and forward completion.

Old-binary/downgrade rollback is rejected. Disposable rollback is drop/rebuild.
For durable data use a reviewed forward fix; a restore requires G1 evidence
and reapplication of all later erasure/retention decisions before exposure.
Never restore erased personal data simply to roll back a feature.

For Redis cutover, run `... retire-legacy-cache --cursor <cursor>` repeatedly
from 0 until `next_cursor=0` while old writers are stopped. This bounded
one-time scan removes the retired unversioned message/pending-action keys;
there is no global flush or permanent namespace scan. Verify historical
content logs separately. `... retention` runs one bounded DB cleanup batch.

### Notice admission follow-up

A freeform turn needing the notice now closes its ingress transaction before
opening the reminder session or awaiting Telegram. Four separate-session
PostgreSQL regressions (unacknowledged, repinned, unavailable and retired)
reproduced the previous self-block with a 300 ms lock timeout and pass after
this repair. No user text/event reaches Coach before acknowledgement.

An in-process LRU hint (at most 10,000 user entries per worker, keyed by database
engine/user and bound to deployment/notice IDs) avoids repeated receipt SELECTs
for an unchanged accepted version. Only a root transaction commit promotes a
positive observation; rollback, abandoned sessions and savepoint commits do
not. Deletion invalidates the entry and prevents an earlier in-flight hint
from resurrecting it. Eviction/restart causes a conservative database reread.
Each admission still checks current access, deployment pin, notice availability
and exact body digest in PostgreSQL. Repinning requires the new exact receipt;
this cache never authorizes access or acknowledges another version. There is
no new schema or durable migration. This reduces receipt lookups, with no
claim of measured production throughput; general load evidence remains B8/B9.

Follow-up checks: 34 disposable PostgreSQL/Redis privacy scenarios passed;
69 focused privacy/access unit checks passed. The SQL observer proves five
separate admitted sessions perform one acknowledgement SELECT after a cold
start, then a changed version requires a new receipt. Transaction tests cover
rollback, savepoint/root commit, invalidation during a staged read, abandoned
session reuse and another user. The original independent local inventory is
kept separate from the GitHub-only P1; the new delta receives its own review.
