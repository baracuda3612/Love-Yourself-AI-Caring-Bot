# WP-03.2 — Correct deterministic plan generation

**Status:** `VERIFIED` — founder merged PR #261 on 2026-10-07 as `758b119773c62dbbd7f2c5f725cfb6e65f42aaeb`. **Implementation branch:** `wp/03.2-deterministic-plan-generation`. **Integration base:** `c76e5489fed7c9db7342f49104a834e2be423328` (founder-merged PR #260).

## Objective and selection contract

The existing DB Content Library is the only runtime content authority. Activation uses the next positive `AIPlan.cycle_number` as its stable discriminator, under the existing per-user lifecycle lock. For the same user, cycle, recipe, catalogue and shown-history snapshot, the builder returns the same ordered exercise IDs, exact content versions and content snapshots. Draft UUIDs and activation timestamps are outside this selection guarantee. A new cycle uses a new deterministic draw; if it accidentally reproduces the previous comparable DAY sequence, retry deterministically until that sequence differs. A SHORT→MEDIUM switch may repeat individual exercises from the five-item pool but must not replay the previous SHORT DAY sequence in MEDIUM days 1–7.

Carry cooldown across boundaries from the latest previous plan's **shown** steps, proven by the durable `step_delivered` lifecycle receipt. A later completed, skipped, expired or canceled status does not erase delivery; a pending step that expires without delivery is not shown. Never use response outcomes, feedback, scores, response times or streaks as selection inputs. Base the next cycle's day 1 on the last shown logical day, preserving one-day cooldown for every currently released exercise. Within a cycle, the shared DAY/EVENING cooldown state remains and allowed every-other-day repetitions remain valid. If no previous exercise was shown, there is no inherited cooldown. Changes to future scheduling, delivery and feedback semantics are outside this package.

`source_exercises` is the distinct set of IDs actually scheduled, in first-use order. Each step keeps the exact eligible DB `(exercise_id, content_version)` and payload snapshot; activation's existing exact-version check remains. The eligible initial pool remains eight exercises, five `switch`; `cold_water_face` stays gated by DG-02. Selection is uniform among candidates after cooldown. No `weight`, difficulty grading, adaptation flag, or hidden behavioral personalization is introduced.

## Acceptance and boundaries

Test identical rebuilds of one cycle, different consecutive cycles, SHORT→MEDIUM first-week non-replay, shown-history cooldown across a completed cycle and an early switch, permitted within-week repeats, no behavioral-outcome influence, `source_exercises`, exact version/snapshot and existing first-SHORT/MEDIUM-evening/no-candidates invariants. Rehearse persistence with fresh disposable PostgreSQL databases; touch no durable data. Preserve B1/B2 lifecycle/event ownership and do not expand into WP-03.3–03.5, WP-06 or broad legacy cleanup. The 21 known completion CTA/report/metrics failures belong to the existing baseline.

If the eligible pool cannot build a replacement during format switch, the transaction leaves the current plan unchanged. The user-facing reply says the new format is unavailable and the current plan was not changed; it does not imply an immediate retry will fix an unavailable catalogue. The same truth applies to direct switch, retained-switch recovery, and the evening-time cascade.
