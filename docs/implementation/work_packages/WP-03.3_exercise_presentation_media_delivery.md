## User outcome and founder clarification (2026-10-07)

Exercises are commodities; a useful moment (founder's target: more than 50%
timing fit) and speed to usable value are the product's win conditions. This
package removes presentation friction: one ordinary message, exact instructions
readable immediately, two existing actions, no heavy UI, additional navigation,
LLM call, runtime media hashing, or transcoding. It does not change timing or
selection policy or claim the timing target has been measured.

Use the three unchanged approved GIFs, complete captions shown above media, and
reuse Telegram animation file IDs after confirmed upload. Cache identity includes
bot identity and the exact exercise/content/asset revision and digest; it is a
disposable process optimization, never a content or delivery authority. Cold
startup can upload again. No Redis/DB cache dependency or new persistent schema.
Client download/playback under a fraction of a second on weak networks is a
device acceptance goal, not a guarantee from a Bot API receipt. Instructions must
be usable even with autoplay disabled or a three-second media delay. Real-device
text/caption/thumbnail and weak-network checks remain DG-03 before beta.

## Implementation boundary

* One structured `ExercisePresentation`: exact exercise ID/content version,
  title, duration label, ordered steps, media metadata, current status, localized
  action deadline and available actions. Read exact eligible versions from DB;
  preserve WP-03.1 medical/activation gates and WP-03.2 selection/snapshots.
* A pure HTML renderer: scheduled first line `Пауза`, escaped dynamic fields,
  no category/slot/mechanic/rationale/counters/frames. Separate 4096 text and
  1024 caption bounds after entity parsing, conservatively measured in UTF-16.
  Never truncate steps. Invalid/oversize full text fails before any send.
* Versioned local GIF upload without hash verification in the delivery adapter.
  Full caption overflow or definite media failure attempts the same full text.
  Timeout/network/server errors are uncertain: return uncertainty, no duplicate
  fallback or retry. If text fails, never return successful delivery.
* Successful result returns actual `gif`/`text` variant, rendered payload,
  presentation and Telegram chat/message identity. WP-03.4 owns durable receipts,
  variant/payload persistence in `exercise_deliveries`, and reconciliation.
* Scheduler uses the canonical adapter and preserves existing lifecycle/event
  authority, callback IDs and expiry window. Uncertainty must not mark delivered.
  Old persisted jobs retain callable/argument compatibility.
* Coach receives canonical facts only for a receipt-proven scheduled message,
  scoped to its user and current plan. Existing Coach message construction must
  forward the facts. There is no implemented on-demand entrance in this base:
  expose the same exact-version presentation builder for WP-06 without inventing
  selection, occurrences, callbacks, or state aggregates now.
