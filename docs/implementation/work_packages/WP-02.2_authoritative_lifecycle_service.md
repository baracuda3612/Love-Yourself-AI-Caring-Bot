## Objective

Make `app.lifecycle` the single backend boundary for authoritative current
status, activation, terminal step transitions, expiry, pause/resume/cancel,
time reconciliation, and the stable plan-format and continuation interfaces
needed by later packages.

Every mutation re-reads persisted state under the user/aggregate lock, enforces
the current owner and entitlement facts, records a stable operation result, and
returns structured post-commit work. Persistence helpers do not send Telegram
messages or claim scheduler success.

## Audit coverage and dependencies

This package implements `LIF-01`, `LIF-09`, `LIF-16…18` and the WP-02.2 parts
of `FSM-06` and `FSM-09`. It establishes the lifecycle boundary needed by
`RT-08` and `RT-11…14` while leaving their detailed UX and schedule semantics
with WP-02.3.

WP-01.3 provides plan/step authority, row invariants, and lifecycle operation
receipts. WP-01.4 provides the event-operation boundary used by expiry. WP-02.1
removed the dead FSM, schedule-adjustment tunnel, and producerless mutation
paths before this consolidation began.

## Non-goals

This package does not implement WP-02.3 runtime-control UX, semantic time
collection, pause/resume re-anchoring, paused completion policy, or post-abort
follow-up. It does not implement WP-03.4 scheduled-delivery reconciliation or
WP-03.5 durable completion/automatic continuation. It does not add the target
content library, feature-wide instrumentation, destructive schema cleanup,
Railway migration, deployment, secret inspection, or real-data mutation.

## Implementation decisions

### One persisted-decision boundary

**Context:** live callers mixed direct status writes, guard modules, schedule
helpers, and a finalization side-effect wrapper.

**Decision:** `app.lifecycle` owns every live persisted lifecycle decision.
Builder/finalizer and time-slot modules are internal persistence/calculation
helpers only; they are not exported runtime entrances.

**Reason:** one lock and receipt protocol is reviewable and prevents different
surfaces from accepting contradictory state.

**Consequence:** `app.plan_guards` and `app.plan_pause` are deleted, and static
reachability tests reject direct status writes outside `app.lifecycle`.

### Commit before external reconciliation

**Context:** APScheduler and Telegram cannot participate atomically in the
PostgreSQL transaction.

**Decision:** lifecycle methods return typed `ExternalEffect` intents. Callers
commit the decision first, then reconciliation re-reads targets and returns
`succeeded`, `failed`, `deferred`, or `not_required`.

**Reason:** a persistence helper must not swallow an external failure and return
success, and a replay must be able to retry the same outstanding effect.

**Consequence:** activation, time changes, and cancellation expose partial
failure honestly. Expired Telegram keyboards retain `tg_message_id` until a
confirmed edit and are retried by the expiry reconciliation scan.

### Explicit deferral seams

**Context:** WP-02.2 must expose stable interfaces without implementing behavior
whose prerequisites belong to WP-02.3 or WP-03.5.

**Decision:** pause/resume schedule effects and plan-format switching return
explicit deferred results; `prepare_continuation()` validates the exact owned
completed plan without creating a successor.

**Reason:** a typed seam prevents later packages from inventing another
authority while preserving the approved dependency order.

**Consequence:** current copy no longer claims that resume already restored the
schedule. Automatic continuation and detailed control behavior remain absent.

## Earlier configured review dispositions through `60876d7`

* **P1, MEDIUM activation cascade:** valid. The cascade now preserves the
  original activation source ID across evening-time collection, checks the
  structured activation result, keeps the pending action on reconciliation
  failure, and returns partial-failure copy instead of success. Focused
  regression tests cover source preservation and the failed reconciliation.
* **P2, stale scheduler run date:** valid. Schedule reconciliation now compares
  the actual APScheduler `next_run_time` with authoritative `scheduled_for`.
  A stale job is removed and reconciliation returns failure instead of success;
  a focused regression test covers the past-time/stale-job case.
* **P2, inactive text sender:** valid and caused by WP-02.2 entitlement
  enforcement. The orchestration boundary now catches
  `LifecycleEntitlementError` before Coach routing and returns a deterministic
  access-denied reply. Full enrollment/access UX remains deferred to WP-04.1;
  a focused regression test proves that Coach is not invoked.
* **P1, inactive sender with no plan:** valid follow-up to the preceding fix.
  The completion preflight now enters `require_lifecycle_entitlement()` before
  its no-plan return, so an inactive sender cannot reach onboarding or Coach.
* **P2, replayed cancellation plan type:** valid. The abandon replay reloads
  the owned persisted plan and restores its SHORT/MEDIUM type, preserving the
  original seven- or fourteen-day cancellation result while retrying scheduler
  reconciliation.
* **P2, concurrent completion delivery:** valid and introduced when WP-02.2
  made the completion effect replayable. Per-plan attempts now serialize within
  the approved single runtime owner and re-check the durable sent receipt after
  waiting, preventing overlapping entrances from sending the same report twice.
  Cross-runtime durable completion orchestration remains WP-03.5.

## Independent audit dispositions after `60876d7`

* **P2, activation replay argument drift:** accepted. Activation receipts now
  reserve a compact fingerprint of the requested plan type and resolved
  day/evening times. A reused source ID with different material arguments fails
  closed, while an exact replay returns the recorded `active` outcome even if
  the plan later became terminal.
* **P2, superseded time-change propagation:** accepted. Day/evening runtime
  tools and `/user/time-slots` return a non-success superseded disposition with
  the authoritative value, and skip scheduler reconciliation for the stale
  decision. The orchestrator no longer emits time-change success copy for it.
* **P2, unreserved deferred interfaces:** accepted. Plan-format and continuation
  seams now write durable receipts with their target plan and material result,
  return exact replays as duplicates, and reject cross-operation, target-plan,
  or requested-format drift without implementing WP-02.3/WP-03.5 behavior.
* **P2, pre-catalog ignored-event chronology:** accepted. A legacy expiry before
  `task_ignored` catalogue activation still terminalizes the authoritative
  step, but records no invented historical event. Per-candidate savepoints
  isolate other event-validation failures so one legacy row cannot abort the
  remaining overdue sweep.
* **P2, replay reconciliation includes past pending steps:** accepted. Exact
  time-change replay now reconstructs only current future pending scheduler
  targets; a pending step that became past no longer turns the valid replay
  into `schedule_reconciliation_failed`.

## Integrated remediation after `6177354`

The 13 confirmed audit findings were remediated through five shared contracts,
without a migration or a second durable authority:

* W1 writes versioned activation receipts over canonical submitted material,
  retains bounded readers for base `active` and candidate `active:<digest>`
  receipts, provides recorded-plan activation recovery independent of Coach
  call IDs, canonicalizes time receipts, and makes format replay receipt-first;
* W2 reconciles one complete active-plan job set, proving eligible future jobs
  exact and obsolete deterministic jobs absent instead of carrying partial
  step-ID target lists across retries;
* W3 keeps requested, authoritative, applied/superseded, and external-effect
  state separate across API, runtime tools, and user copy; paused schedule work
  remains explicitly deferred to WP-02.3;
* W4 preserves authoritative expiry when optional telemetry is rejected for an
  expected catalogue chronology or supported legacy-content linkage reason,
  while unexpected invariant/storage failures remain failures;
* W5 retains a confirmed completion send in the current-runtime guard and
  retries only its durable sent receipt. Cross-runtime certainty remains
  explicitly deferred to WP-03.5.

Remediation verification on the final working tree: `81 passed` focused,
