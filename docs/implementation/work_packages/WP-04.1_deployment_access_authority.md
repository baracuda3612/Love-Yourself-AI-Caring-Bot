## Bounded execution contract

One access service extends the WP-01.4 tables. Restricted access records own
identity, accepted roster, entitlement, invitation and enrollment. Telegram,
`users.is_active`, URL parameters, Redis and telemetry cannot grant access.
Production identity proof uses authorization-code OIDC (Google/Microsoft) or
single-use verified email. Microsoft email claims alone are not proof of
mailbox control: email verification is required unless an already verified
stable provider subject is bound. Only current roster members receive grants.
No mailbox, directory, calendar or profile scope is requested.

Roster imports require authenticated operators, bounded JSON input, declared
mode and expected total, a stored preview, exact-count confirmation, expiry and
current-version comparison. Only confirmed full snapshots revoke by omission;
deltas contain explicit additions/revocations. Accepted versions remain as
access-only audit/rollback input, including explicit no-op delta revocations.
Operators can preview/apply rosters, revoke entitlements and set controls before
launch or after commercial end; member access and token issuance still require
an active commercial period. Reconciliation cadence never expires access.

Handoff tokens contain 256 random bits, are environment/key-version scoped,
hashed at rest and valid for ten minutes. Issuance is separate from roster
apply. Redemption locks current authority, consumes once and creates/resumes
one enrollment. One Telegram account and one entitlement each have at most one
active enrollment. Rebinding is operator-only after renewed identity proof;
no self-service recovery or history transfer is introduced.

All product ingress and sends check current enrollment, entitlement, commercial
period and environment. Deployment enrollment and delivery switches stay
orthogonal. Returning enrolled users need no SSO. Revocation preserves history.
Signed Telegram WebApp data authenticates time-slot callers; ownership, current
access and rate limits precede schedule mutation. Idempotency remains in the
lifecycle service. Enrollment responses never echo secrets, use no-store and
no-referrer, and have CSRF/browser binding. Request logging must exclude
enrollment query strings, bodies and authorization headers.

Testnet is founder-issued and runs the same artifact/downstream flow with
separate resources and keys. Runtime environment binding requires no existing
product rows beyond migration catalogue and approved content reference data;
the isolation inventory fails closed on
reused/mismatched infrastructure. Re-enabling delivery wakes due-step recovery
after the control change commits, while each send still checks current access.
Timezone resolution
uses explicit user override, otherwise deployment default in single mode;
distributed mode requires the later onboarding timezone choice before planning.
Late send receipts use the attributed enrollment's deployment timezone rather
than a replacement enrollment's current default.

## Migration, compatibility and rollback

Forward migration extends existing primitives and adds bounded proof/preview
state and unique current-authority indexes. No historical user receives an
invented entitlement. Stop old runtime, migrate, bind the fresh environment,
start only the exact-head artifact. No old-binary rollback. Development rollback
is drop/recreate of disposable DBs; durable rollout requires Gate G1 and a
reviewed restore/forward-fix plan. No Railway/company enrollment or testnet
history promotion is authorized here. Release/medical/device gates remain open.

## Scoped review repairs

The first independent read-only review of `37107a0` against integration merge
base `340561b` found one P1 and four P2 defects. All are accepted and repaired:

* New recorded events capture the historical enrollment and aggregate dimensions.
  Send receipts additionally carry `attribution_at` from the authorized send
  claim, while `occurred_at` remains the actual receipt time. The existing
  catalogue/FK/immutable-event controls remain; membership/commercial coverage
  uses the claim basis for delayed send facts. Replay preserves the original
  attribution, including truthful legacy nulls. No historical event is backfilled.
* OIDC state consumption commits before network exchange/JWKS work, and final
  grant revalidates current authority in a separate short transaction. Failed
  exchanges leave state spent. Roster preparation uses bulk identity/entry
  operations and current-version/policy checks; atomic apply bulk-updates grants.
* Coach and pulse sends recheck access after slow generation and release locks
  before Telegram I/O. A denied reply is not sent or stored. Actual in-flight
  exercise/completion receipts continue to commit after access changes.
* The legacy completion page has one truthful "return to bot" link instead of
  stale plan-selection promises. No parameterized legacy entry is restored.
* `timezone_override_explicit` distinguishes new explicit choices from unknown
  legacy timezone values; old data stays intact but cannot override the current
  deployment default or bypass a distributed-mode choice.

A separate author-discovered revocation defect is also repaired: repeating
identity proof cannot undo an access-only manual revoke. Restoration requires

## Final conversational send guard — latency follow-up, 2026-10-17

The final Coach/pulse access check uses one fresh SQL authority snapshot and
returns its database timestamp. It does not take a deployment row lock, call
SSO/LLM/providers, or cache access. This read-only boundary makes no associated
state mutation; lifecycle mutations and durable exercise/completion send claims
retain their existing transaction locks. Revocation is checked at the final
snapshot before external I/O, with the same possible post-check race as any
guard that releases its locks before sending.

Ten access-state cases verify owner activity, enrollment, current entitlement,
commercial end, environment and the independent delivery/enrollment switches.
They assert exactly one SQL statement; a separate held-deployment-lock case
proves that unrelated replies do not queue on that lock. Fresh disposable
PostgreSQL access suite: 65 passed. Default suite: 480 passed / 233 opt-in skips.
The paired local benchmark includes pooled-session creation/rollback and
compares four SQL statements with one, using 100 sequential and 160 requests
across eight workers. It is comparative local evidence, not a production SLO.

## Audit follow-up — 2026-10-17

The full-candidate audit of `5ff7db5` confirmed five scoped defects. The repairs:

* Microsoft relies on its validated stable `sub` and tenant, without requiring
  the unused `oid` claim or expanding `openid email` scopes. If `email` is
  absent, the consumed OIDC flow leads to the existing browser-bound email
  form; no email is inferred and no entitlement exists before mailbox proof.
* Google accepts only its two documented issuer strings and canonicalizes them
  for stable subject binding. Real RSA validation and cross-issuer repeat proof
  preserve signature/issuer/audience/nonce/domain and roster checks.
* Support replacement requires the expected current enrollment. Ordinary
  replacement stays within the same identity/deployment; a deliberate change
  requires `identity_change`, a distinct immutable operator audit action and
  the target entitlement recorded on the ended enrollment. No history moves.
* Pending completion and successor scheduling for inactive users are parked by
  matching wake/due predicates. Reactivation makes unfinished work eligible;
  already in-flight sends still reach bounded unknown-send quarantine without
  resend. Confirmed receipts remain durable independently of current access.

Post-fix evidence: 481 default passes / 243 opt-in skips, 72 fresh disposable
PostgreSQL access scenarios, 69 completion scenarios, full fresh migration
rehearsal, compilation, dependency consistency and diff checks. The newly added
support audit action is included in the unreleased access migration constraint.

The existing long-lived report/pulse bearer-link issue retains its explicit

The original GitHub inventory is not relabeled as independent local discovery.

## Silent-reminder remediation — 2026-10-21

The scheduler records a distinct `silent_send_attempted` operational fact before
Telegram I/O. Confirmed `silent_sent` remains a separate immutable receipt with
the fresh claim timestamp and actual occurrence. The queued coroutine performs
the one-statement delivery-access check immediately before dispatch and owns the
receipt write even when the scheduler's 30-second wait expires. Attempts, including
unknown outcomes, share the existing six-day re-engagement cooldown; a definite
failure may therefore skip that optional reminder. Failed receipt persistence is
logged, while the attempt still prevents automatic duplicate outreach. This does
not change durable exercise/completion send claims or conversational reply cost.

Acceptance evidence for this remediation: 490 default passes / 244 opt-in skips;
73 WP-04.1 and 69 B3 completion PostgreSQL scenarios on fresh disposable
databases, plus compilation and diff checks. Independent remediation review is
still required before updating PR #269 or recommending merge.
