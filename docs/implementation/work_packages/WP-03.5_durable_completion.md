# WP-03.5 — Durable completion and automatic continuation

Base: `f9cb11a5aba7ba1887e9ac4cdce96181224d4ad8` (PR #266 merged).

## Execution contract

The authoritative lifecycle boundary closes the explicit owned plan only
when all its steps have proven terminal facts. Completion, one plan-scoped
summary obligation, and one same-format target-builder successor commit together.
Failure rolls back this transition, never the already committed Done/Skip.
Replay addresses the source plan, independently of the current/latest plan.

Done/Skip triggers immediate post-commit completion (target <2 minutes). If expiry
is the last terminal fact, report time is the next selected working day at the
saved DAY time in the user's timezone. The successor starts on the next selected
working day strictly after the report day. Its real first scheduled datetime is
the only source of a future delivery promise. Late known-failure retries move
unstarted successor work beyond the actual report day before making a promise.
User controls supersede previous schedule promises; pause/cancel/switch never
get undone by a stale completion replay.

The obligation, not events, process memory, or APScheduler, owns report delivery.
A committed send claim fences duplicate workers. An interrupted or ambiguous
send is quarantined, never resent. Recovery only visits unfinished work, parks
at its useful deadline, and shuts down when no automatic work remains. The
fixed UTC cron is an isolated backstop for terminal active sources.

Inherited invariants: immutable exercise receipts and exact content versions;
one exercise/message; atomic owned actions/expiry/events; completed-only feedback;
delivered unexpired exercises remain actionable while paused; unknown exercise
sends never resend; worker dispatch does not block polling; medical gate DG-02.

Non-goals: final WP-07.4 summary image/web payload, WP-07 canonical metrics,
retention/engagement, new formats/content, on-demand, LLM delivery, broad cleanup.

## Founder-approved uncertain-summary fallback

A summary with an uncertain result blocks successor exercise delivery. After a
10-minute TTL the user may explicitly call `/continue_plan`. The command does
not resend the summary. It sends a separate factual confirmation with a newly
resolved future first-task datetime, and only a confirmed receipt releases the
successor. An uncertain fallback also waits for the TTL and another explicit
user command; there is no automatic resend. Recorded on 2026-10-14.

## Implementation and bounded repairs

`plan_completions` owns one source/successor identity, delivery claim, actual
summary receipt, and the explicitly requested recovery confirmation. Unknown
outcomes have no automatic retry. Known rate limits and preparation failures
have a three-attempt budget. Failed/uncertain work has no background wakeup;
user recovery is available after the TTL. Pending scheduled work parks at its
exact deadline; unfinished source-builder failures retry after five minutes.
No scheduler scan opens user sessions for already repaired completion history.

Two inherited defects became reachable at the new seam and received bounded
repairs: activation now records its actual instant independently of a future
start date, allowing immediate cancellation/switch; changing delivery time
keeps each existing calendar date instead of adding its logical day twice,
and recomputes expiry while leaving delivered work untouched.

A confirmed response arriving after its promised start day retains its receipt
but holds automatic exercises until explicit future-date reconfirmation. A
user pause/cancel/format switch is re-read before report generation; replay
never resurrects or replaces that decision. Explicit format switches retain
the existing user-requested activation behavior and supersede automatic copy.

## First runnable activation telemetry — 2026-10-15

Accepted GitHub P2 on `9d04b23`: a successor created paused, cancelled or
superseded before report confirmation must not contribute a runnable activation.
The founder clarified that automatic `plan_activated` means the first successful
active, unblocked exercise schedule, while the domain plan and its `activated_at`
may already exist. Current paused/active counts remain queries of plan status.

The completion event now belongs to `reconcile_plan_schedule`, inside the same
user lock as the exact job-set proof. It requires active entitlement, an active
plan, a released report gate, future pending work and no scheduling failures.
Initial release, first resume and receipt retries share this path. The stable
`plan-activation:<id>` key preserves one event and one aggregate contribution;
event occurrence is the first successful scheduling instant, not builder time.
Builder-activation receipt recovery defers automatic-successor instrumentation
to that same gate. Paused/cancelled successors park without activation; existing
manual activation instrumentation and domain chronology remain unchanged.

The category review found a second P2: if activation telemetry fails after
resume installs jobs, a previously parked completion row provided no unattended
retry. Resume now arms the existing `schedule_pending`/`wake_at` obligation in
its authoritative DB transaction, before external work, and emits the existing
completion-alarm effect. Recovery can retry the locked proof without a user
action, then clear the obligation and park. Exact resume replay can re-arm a
failed alarm while that concrete obligation remains outstanding. No new state
or recurring history scan is introduced.

The same category review identified a P3 in persistent failure pacing. A failed
event attempt now retains its obligation with a wake time at least 30 seconds
later. A savepoint preserves the paired event/contribution atomicity; obligation
clear/retry belongs to the same user lock as the job proof. Per-successor errors
do not block other users, and the failure alarm cannot collapse into one-second
retries for an overdue row. Recovery parks after the concrete work succeeds.
The final category closure review passes all affected surfaces, with the P2
lost-obligation and P3 pacing findings fixed and no further qualifying findings.

Verification passes 66 completion and 13 runtime-control PostgreSQL scenarios
