## Transaction and failure boundaries

1. Private actor and owned environment/enrollment checks precede personal
   reads and mutations. Every menu callback rechecks authority, including
   callbacks from old keyboards. Rights/support remain reachable after
   corporate access loss. Erasure does not recreate an account.
2. Setup answers and stage changes commit together under the user lock.
   Invalid input preserves accepted choices. Stage revision fences callbacks.
   The last setup message id fences duplicate/out-of-order text, including
   transport retries after setup completion.
3. Setup creation uses the stable operation `onboarding:first-plan`.
   The finalizer completes setup in the same transaction as finalized plan,
   steps and operation receipt. Errors roll the entire activation back.
4. Scheduler work and Telegram I/O occur after the transaction closes.
   Reconciliation precedes a truthful confirmation. A repeated confirmation
   recovers the existing first plan, never another activation.
5. Active calendar edits preserve delivered and already-due steps and
   immutable delivery attempts. Future pending groups start on the next
   selected local day after today. Attempts on affected future steps fence
   mutation. The editor states the next-day behavior.
6. Active calendar mutation saves preferences, updates pending schedules and
   expiry, increments the plan version and records an input-bound idempotency
   receipt. Report timing is refreshed only where the existing completion
   contract permits; report-before-successor blocking remains authoritative.
7. Pause/resume and format changes re-read actual post-effect state. A stale
   plan target/version cannot change a later plan. Format replacement keeps
   the existing plan until the canonical operation is ready.
8. Menu text intent is bound to the actor's enrollment, exact notice, plan
   version where relevant, expiry and last message id. Cancel/navigation
   closes the intent. Invalid values remain in the same editor. Unsent
   Telegram draft text is unavailable to the bot.
9. Only the explicitly submitted feedback text is stored as feedback.
   It is not copied to conversation history or passed to Coach. Its
   Telegram-source receipt is unique and bound to the owning actor.
   Existing retention/export/deletion rules apply.
10. Enrollment responses remain neutral about roster membership. CSRF,
    rate limits, browser proof, environment isolation and single-use Telegram
    handoff stay in WP-04.1. Product CSS is allowed by an exact CSP hash.
    Screenshots use fixture-only pages, never real email/provider accounts.

to discard direct feedback that an earlier schema cannot represent.
