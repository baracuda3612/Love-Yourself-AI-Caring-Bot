## Objective

Turn the inspected WP-01.1 physical schema into one bounded target contract
before any lifecycle, event/privacy, content, or occurrence migration begins.
The contract must name one durable database authority per mechanism, classify
derived values, bound Redis to expiring transient state, and make deferrals
explicit so later packages do not create parallel truths or partial systems.

## Delivered contract

The canonical design is
`docs/implementation/target_schema_invariant_ledger.md`. It defines:

* target retained/reshaped/added/deferred/removed tables and foreign-key
  deletion behavior;
* stable enum vocabularies and evolving catalogue boundaries;
* named partial unique, idempotency, range, chronology, and state constraints;
* only query-backed/integrity-critical indexes, with broad tuning deferred;
* exactly one database authority for content, lifecycle, deployment,
  entitlement, occurrence, events, feedback, notice acknowledgement, report
  grants, and aggregates;
* `calculate`, `immutable_snapshot`, or `remove` for every high-risk duplicated
  or derived field family;
* two target Redis session namespaces, both environment-scoped, versioned, and
  TTL-bounded, with PostgreSQL fallback/failure semantics;
* explicit future owners for lifecycle, event/privacy/deployment, content,
  sensitive cleanup, on-demand occurrence, delivery reconciliation, and
  harmless legacy cleanup.

The package adds a structural contract test that rejects missing/duplicate
mechanism authorities, an unapproved derived-field classification, non-versioned
or unbounded target Redis keys, or a missing required deferral.

The companion planning model
`docs/implementation/wp_01_2_unit_economics.md` tests the contract against
current public Railway/OpenAI prices at 100, 1,000, 10,000, and 100,000 MAU.
It does not turn estimates into product quotas or a billing system; measured
cost telemetry, capacity tests, and pilot pricing remain with WP-05.3,
WP-09.2/WP-09.4, and WP-10.1 respectively.

## Authority decisions

* `content_library` is the one released content authority. Its target identity
  is `(exercise_id, content_version)` and released copy is append-only. Plan and
  delivery copies are immutable historical snapshots, never current catalogue
  writers.
* The plan aggregate rooted at `ai_plans` is lifecycle authority;
  `ai_plan_steps.step_status` owns child execution. `current_mode` is calculated
  once, and stored user/profile/Redis lifecycle duplicates are removed by their
  owning packages.
* `deployments`, `access_entitlements`, and `deployment_enrollments` are
  distinct authorities for launch configuration, sponsored access, and
  historical user attribution. No permanent `users.deployment_id` is allowed.
* `user_events` owns personal event facts. Explicit integer plan-step identity
  and composite content identity replace mixed `step_id`; no facts are invented
  during backfill.
* `aggregate_records` is one aggregate authority with bounded personal
  contribution rows and one-way immutable sealed cells. Sealed rows contain no
  user/event/operation join key.
* `feedback_events`, `notice_acknowledgements`, and `report_access_grants` own
  their respective facts; chat, logs, URL possession, signed plan IDs, and
  Redis do not.
* `on_demand_exercise_requests` is the named occurrence authority but remains
  deliberately absent until WP-06.1.

## Boundaries preserved

This package did not:

* add or run an Alembic revision;
* change current ORM models, runtime writers/readers, Redis code, or Railway;
* start the WP-01.3 lifecycle migration or WP-01.4 primitives;
* repair or widen `SCHEDULE_ADJUSTMENT`;
* adopt `apscheduler_jobs` into Alembic;
* simplify PlanDraft storage, build a generic outbox/lock framework, unify
  database pools, add leader election, or tune indexes broadly;
* delete harmless legacy tables or sensitive rows without the owning migration
  and evidence.
